Lab 6 - Parsing the Mini Language with Yacc

1. What the lab does

The program is first scanned by the scanner from Lab 5 (which uses the FA for identifiers and constants). This produces the PIF and the ST.
Then the PIF is given to yacc token by token, and yacc checks whether the program follows the grammar.
If it does, the output is the string of productions that were used, which shows how the program is derived from the start symbol.
For yacc I used PLY (Python Lex-Yacc). It works the same way as yacc/bison, but it is written in Python, so I do not need flex and bison on Windows.
PLY builds an LALR(1) parser from the grammar, just like yacc does.


2. The grammar

The grammar is G = (N, Sigma, P, S).

N (nonterminals):
program, statement_list, statement, decl_stmt, type, assign_stmt, variable, input_stmt, output_stmt, expression_tail, return_stmt, if_stmt, else_part, while_stmt, def_stmt, parameters_opt, parameters, parameters_tail, call_stmt, expression, add_expr, mul_expr, math_expr, term, function_call, squad_access, squad_literal, arguments_opt, arguments, arguments_tail, condition, add_op, mul_op, math_op, comparison_op

Sigma (terminals): the reserved words and the two tokens that come from the PIF.
RECRUIT, AS, NUMBER, SQUAD, INHERITS, AT, SHOVE, GRADES, AND, STEAL, CONVICTED, GUILTY, INNOCENT, APOCALYPSE, GRIND, NONSTOP, CREATE, FROM, TOO, GENESIS, GANG, SCATTER, SIMILARITY, DIFF, STATS, ANNEX, INDEPENDENCE, MULTIPLY, SPLIT, BONUS, SAME, OPPOSE, MOG, MOGGED, HTN, LTN, identifier, constant

S (start symbol): program

Identifier and constant are terminals here because the scanner has already checked them with the FA from Lab 4, so in the PIF they only appear as id (code 0) and const (code 1).
This is also why the rules for letter, digit, number and string from Lab 2 are not part of this grammar: they belong to the lexical level, which is handled by the scanner.

3. What I changed from the Lab 2 grammar

The statements are the same as in Lab 2.
The expressions were previously written as add_expr ::= mul_expr add_rest and add_rest ::= add_op mul_expr add_rest | epsilon. That form works well for a top-down parser, but yacc is a bottom-up parser and works better with left recursion, so the rule is now add_expr -> add_expr add_op mul_expr | mul_expr (and the same for mul_expr and math_expr).
The new rules describe the same language, and with left recursion the operators on the same level are evaluated from left to right, as specified in Lab 2.
The order of operations stays the same: math_op (SIMILARITY, DIFF, STATS) first, then mul_op (MULTIPLY, SPLIT, BONUS), then add_op (ANNEX, INDEPENDENCE), and comparisons are only allowed in conditions.
String and number were replaced by constant, and the character-level rules were moved to the scanner.

The grammar has no conflicts in PLY (no shift/reduce or reduce/reduce conflicts), so it is LALR(1).


4. How scanning and parsing work together

The file parser.py calls scan() from scanner.py, which writes the PIF, ST and errors files, as in Lab 5.
If there are lexical errors, the program stops there, because there is no point in parsing a program with invalid tokens.
Otherwise, PifLexer goes through the PIF and gives yacc one token at a time (this is normally the job of lex):
The token id becomes identifier, const becomes constant, and a reserved word stays the word itself.
The value of an identifier or constant is taken from the ST using the position stored in the PIF, and it is used in the error messages.

Each production in grammar.txt becomes a rule for yacc. Whenever yacc reduces using a production, its number is saved.
Yacc works bottom-up, so the sequence of reductions is a rightmost derivation in reverse order. Reversing the list gives the rightmost derivation from program down to the program text, which is the string of productions.

If the program has a syntax error, the parser reports the line and the token where it stopped.


5. Example

For p1.txt, the string of productions starts like this:
1 2 2 2 2 2 3 6 19 17 ...
Production 1 is program -> statement_list, then production 2 appears five times because there are five statements, and production 3 is the epsilon at the end. After that, the last statement is expanded first (since the derivation is rightmost): SHOVE n uses 6 (statement -> input_stmt), 19 (input_stmt -> SHOVE variable), 17 (variable -> identifier), and so on.
The full output is in output/p1_productions.txt, where each step is also written out next to its production.

p_syntax_err.txt has a missing operand (y INHERITS x ANNEX), and the parser outputs:
syntax error at line 6: unexpected GRADES (GRADES)
